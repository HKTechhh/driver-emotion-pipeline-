Driver Emotion Recognition — technical walkthrough

How the model actually works

An onboarding note on the two emotion-recognition models in this project: how they're built, how they were trained and evaluated, how a camera frame turns into a live prediction, and what changed when we fine-tuned them on a real in-cabin dataset. Every number below comes straight from results/ and docs/experiment_log.md — nothing here is estimated.

01 Overview

Two models, one comparison

The project trains and compares two architectures on the same task — classifying a face into one of several emotions — so their trade-offs (accuracy, size, speed) can be measured directly rather than assumed:

Model A

Custom CNN

A from-scratch convolutional network, built specifically for this task. Small, fast, grayscale input.

Model B

VGG16 transfer learning

ImageNet-pretrained VGG16, adapted with a new head and partial fine-tuning. Larger, slower, color input.

The end-to-end pipeline looks like this:

FER2013 data
28,709 train / 7,178 test face photos
→
Train both models
shared augmentation, class weights
→
Evaluate + stress-test
accuracy, significance, simulated driving conditions
→
Real-time / app
webcam or browser inference

Everything up to here uses FER2013, a dataset of web photos, not driving footage — that gap is exactly what the in-car fine-tuning work in Section 09 exists to measure and close.

02 How it was built

The stack underneath the models

Nothing here is exotic — the project leans on a standard, well-documented Python data-science stack, each tool doing the job it's meant for:

Model building & training

TensorFlow / Keras's Functional API defines both architectures layer by layer (Sections 04–05); training runs through Keras' own model.fit(), with EarlyStopping, ReduceLROnPlateau, ModelCheckpoint and CSVLogger handling the bookkeeping every run needs.

Computer vision

OpenCV handles image/video I/O, color conversion and resizing throughout; MediaPipe's BlazeFace model does face detection, with OpenCV's own Haar cascade as an automatic fallback if MediaPipe isn't available.

Data & metrics

NumPy and pandas for arrays and tabular results; scikit-learn for classification reports, confusion matrices, and the bootstrap/McNemar significance tests in Section 07; Matplotlib/Seaborn for every chart and curve.

The demo app

Streamlit renders the browser app end to end; streamlit-webrtc streams live webcam video into it for the real-time tab.

Engineering habits that made this reproducible

  • One config.py holds every path and hyperparameter — nothing is hard-coded inside a script, so a run's exact settings are always visible in one place.
  • Every script is a small argparse command with its own main(), runnable on its own (python -m src.train …) rather than through a notebook that has to be stepped through cell by cell in order.
  • A fixed random seed (42) is set at the start of every script, so a training or evaluation run can be repeated and compared honestly.
  • A pytest suite covers the data pipeline, model surgery, and every helper function the app depends on — including regression tests locked in after specific bugs were found and fixed.
  • Actual training happened on free Kaggle GPU sessions (a T4); a laptop CPU was only ever used for quick, small-scale smoke tests before spending GPU time on a full run.
  • Every run, decision and bug is written down as it happened in docs/experiment_log.md — including the ones that didn't work (Section 09's class-weighting attempt, for one) — so a result can always be traced back to exactly what produced it.
03 Data

FER2013: 7 emotions, 48×48 grayscale

Both models are trained on FER2013: 28,709 training images and 7,178 test images, each a 48×48 grayscale face, labelled into one of angry, disgust, fear, happy, neutral, sad, surprise. The test set is never touched during training or model selection.

The dataset is heavily imbalanced. Disgust has only 436 training images and 111 test images, versus 7,215 and 1,774 for happy — about 16.5× fewer. Left alone, a model will mostly ignore disgust because getting it wrong costs almost nothing to the average loss.

The fix is class weighting, not resampling: each class's loss contribution is scaled up in inverse proportion to how rare it is. A first attempt used scikit-learn's standard "balanced" weights — disgust ended up weighted ~9.5×, which blew up gradients whenever a disgust image appeared in a batch and stalled training entirely at chance-level accuracy (~14%). The fix that shipped square-roots the balanced weights and caps them at 3.0 (config.py's CLASS_WEIGHT_MODE = "sqrt"), which keeps the correction without destabilising training.

Light augmentation is applied to the training split only: horizontal flip, ±0.05 rotation, 0.1 zoom, and ±0.2 brightness/contrast jitter — enough to reduce overfitting without distorting what a face actually looks like.

04 Architecture A

Custom CNN — 4.8M parameters

A from-scratch network built from VGG-style blocks, sized for 48×48 grayscale input. Each block is two 3×3 convolutions (with L2 weight regularisation) followed by batch normalisation, ReLU, a 2×2 max-pool, and dropout — repeated four times with growing filter counts, then a lightweight classification head:

Input — 48×48×1 grayscale
× 4 blocks — filters: 64, 128, 256, 512
Conv 3×3 → Conv 3×3 — BatchNorm + ReLU after each
MaxPool 2×2 → Dropout 0.25
GlobalAveragePooling2D
Dense 256 → BatchNorm → ReLU → Dropout 0.4
Dense 7 → Softmax — one score per emotion

Trained for 60 epochs (batch 64, Adam at lr=1e-3) on a Kaggle T4 GPU in 21.5 minutes, checkpointing on best validation accuracy: 66.65% at epoch 59, val macro-F1 0.643. ReduceLROnPlateau fired six times as training plateaued; EarlyStopping (patience 10) never had to cut the run short.

05 Architecture B

VGG16 transfer learning — 15.0M parameters

Keras' VGG16, pretrained on ImageNet, with its classifier head replaced. Grayscale input is converted to 3-channel and resized to 224×224 (VGG16's native resolution) before the shared preprocessing step:

Input — 224×224×3, ImageNet-normalised
VGG16 conv base — 5 blocks, ImageNet weights
GlobalAveragePooling2D
Dense 512 (ReLU) → Dropout 0.5
Dense 7 → Softmax

Training happens in two stages, because randomly-initialised head weights would otherwise send garbage gradients straight into the pretrained base:

Stage 1 — frozen base
Only the new head trains. 15 epochs, lr=1e-3. Plateaus around 50% val accuracy — ImageNet features alone transfer poorly to 48px grayscale faces.
→
Stage 2 — unfreeze block5
The last conv block becomes trainable too (BatchNorm layers stay frozen — see unfreeze_top()). 25 epochs, lr=1e-5. This is the jump to ~66%.

Best validation accuracy 66.00% at epoch 38 of 40, val macro-F1 0.633, after 123.4 minutes on a Kaggle T4 — almost identical accuracy to the much smaller custom CNN despite 3× the parameters and 2× the file size.

06 Training

What both runs share

src/train.py is one shared CLI for both architectures, so the only real differences between the two runs are the ones described above. Everything else is identical:

Shared settingValue
Random seed42 (set_seed, every script)
Train / val split85 / 15, carved from FER2013's train set
Test setFER2013's own 7,178-image test set — never split from, never trained on
Checkpoint selectionbest val_accuracy, not the last epoch
Early stoppingpatience 10 on val_accuracy
LR scheduleReduceLROnPlateau, ×0.5, patience 4

Pixel preprocessing is centralised in src/preprocess.py and imported by both training (src/data.py) and live inference (src/realtime.py, app_collect.py) — one function per model, called from both places, so a live camera frame is guaranteed to be scaled exactly the way a training image was. The custom CNN divides pixels by 255; VGG16 converts to RGB and applies Keras' own vgg16.preprocess_input.

Fear is VGG16's weak point (0.420 vs the CNN's 0.508) — recall drops to 0.331. That matters more than it might look, since fear and angry are the two "alert" emotions the real-time app watches for.

Is the gap real?

A 1.7-point accuracy gap on 7,178 images could just be test-set noise. To check, src/significance.py ran a 2,000-resample bootstrap and an exact McNemar test on the two models' agreement/disagreement pattern: the paired accuracy difference is +1.71 points, 95% CI [0.70, 2.76] — excludes zero, so the CNN's edge is real, if modest (McNemar exact p = 0.0014). Of 7,178 test images, both models agreed on 5,711 (4,052 right, 1,659 wrong); of the 1,467 where they disagreed, the CNN was right on 795 and VGG16 on 672.

Robustness under simulated driving conditions

src/robustness.py re-evaluates both models on the full test set under six synthetic corruptions meant to approximate real driving conditions — not real in-car footage, but a controlled first check:

Low light collapses both models — the CNN's 28.6% is barely above always guessing "happy" (24.7% of the test set), and VGG16's 21.8% is below that baseline. Neither model is usable in the dark as currently trained. Motion blur is the other standout: VGG16 loses 37 points (65.5% → 28.6%) while the CNN loses only 23.5. Head rotation is nearly harmless for both — unsurprising, since training augmentation already includes rotation.

08 Real-time inference

From camera frame to on-screen prediction

src/realtime.py (a standalone OpenCV window) and app_collect.py's live tab (browser, via streamlit-webrtc) both call the exact same predict_face() function, so there is only one inference path to reason about, not two:

1 · Detect
MediaPipe BlazeFace (downloads a small model on first use); falls back to OpenCV's Haar cascade automatically if MediaPipe is unavailable. Confidence threshold 0.6. If several faces are found, the largest box wins.
2 · Crop + pad
Crop the chosen box, expanded 15% on every side, clamped to the frame edges.
3 · Grayscale + resize
Convert to grayscale, resize to the model's expected input — 48px for the CNN, 224px for VGG16.
4 · Preprocess
The same per-model function used in training (Section 06) — never a separate implementation.
5 · Predict
One forward pass → 7 (or 6, for a KMU-FED fine-tuned model) class probabilities.
6 · Smooth
EmotionTracker averages the last 10 frames' probabilities, so one noisy frame can't flip the displayed emotion.
7 · Alert
If the smoothed top class is angry or fear continuously for ≥3.0 seconds, a "stay calm" banner fires.

By default no image is ever saved — only a CSV log (timestamp, predicted emotion, confidence, FPS). A --save-frames flag exists to also write face crops to disk for growing the training set, but it's opt-in, off by default, and each saved filename carries the model's predicted label, not a verified one — see docs/car_deployment_guide.md, Section 8, before turning it on with a real person on camera.

09 In-car fine-tuning

KMU-FED: closing the web-photo-to-cabin gap

FER2013 is web photos, not a driving cabin. To measure that gap directly — and try to close it — both models were evaluated and then fine-tuned on KMU-FED: 1,106 real in-cabin photos, 12 subjects, near-infrared/night-vision-style capture, 6 emotions (no neutral).

The 12 subjects were split at the subject level (8 train / 2 val / 2 test) — never split by image — so no face the model sees at test time was ever seen during training, even in a different expression. The split is seeded (42) and constrained: only 7 of 12 subjects have any disgust images at all, so the split is resampled deterministically until both the val and test sets each contain at least one disgust-covered subject. Full reasoning is in docs/experiment_log.md.

Step 1 — how bad is the domain gap?

Both FER2013 models, completely unmodified, evaluated on KMU-FED's held-out test subjects (the "neutral" logit is dropped and the remaining 6 renormalised, since KMU-FED has no neutral class):

FER2013 accuracyKMU-FED accuracyDrop
Custom CNN67.5%25.6%−41.9 pts
VGG1665.8%36.3%−29.6 pts

A real, large domain gap — exactly what motivated fine-tuning rather than deploying either model as-is.

Step 2 — fine-tuning

For each model: replace the final layer with a fresh 6-unit head, freeze everything except that head and the last convolutional block (unfreeze_top() — the same mechanism VGG16's own stage-2 training used, batch norm kept frozen), and train on the 8 train subjects with heavier augmentation than FER2013's own (rotation up to ~36°, 0.2 zoom, ±0.3 brightness/contrast — under 900 images makes overfitting the default outcome, not an edge case).

Disgust is scarce here too — only 60 of 700 training images, versus 120–160 for every other class. Three imbalance-handling strategies were tried, in this order, each fully evaluated before moving to the next:

StrategyCNN accuracyCNN macro-F1VGG16 accuracyVGG16 macro-F1Disgust (CNN / VGG16)
None58.1%0.51975.6%0.7240/0/0 · 0/0/0

Oversampling (duplicating minority-class training images so every class appears equally often per epoch, letting augmentation give each duplicate a different view) is the current default and the best result for both models on accuracy and macro-F1 together. It's also the only strategy that got the CNN to predict disgust correctly at all — once, out of 20 test images.

VGG16 still can't learn disgust at all — 0.0 precision/recall/F1 under every strategy tried. The likely reason: oversampling only repeats the same 60 real disgust images with different augmented views; it can't manufacture the visual variety that a genuinely larger dataset would. This is a real, current limitation, not a bug to chase further with the same 60 images.

Both fine-tuned models — cnn_kmufed_ft_v1.keras and vgg16_kmufed_ft_v1.keras — are evaluated on only 160 test images from 2 held-out subjects, and each number above is a single training run. Treat 63–77% as a real but noisy estimate, not a tight bound.

10 The demo app

app_collect.py — five tabs, four selectable models

A Streamlit dashboard that doubles as a demo and a data-collection tool. All four trained models — the two original FER2013 models and the two KMU-FED fine-tuned ones — are selectable from one dropdown, and the app adapts automatically rather than having per-model special cases scattered through the code:

  • model_class_names() reads a model's output size (7 vs. 6 units) and returns the right class list, so every badge, chart and dropdown lines up correctly whichever model is active.
  • model_accuracy_info() looks for that model's own KMU-FED test metrics first, then its FER2013 test-set numbers, then a validation-only fallback — so the sidebar accuracy badge always shows a number that's actually about the selected model, never a hardcoded one from a different model.

The sidebar also has six "traffic scenario" toggles (Night Driving, Highway/Freeway, etc.) that reapply one of src/robustness.py's exact corruption functions — the same ones behind the robustness table in Section 07 — so you can preview how accuracy changes under that condition, plus a clearly-labelled, non-validated risk heuristic.

11 Limitations

What this is — and isn't — validated for

  • Disgust doesn't work in the KMU-FED fine-tuned models — 0/0/0 for VGG16 under every strategy tried, and only 1-in-20 correct for the CNN.
  • Low light collapses both original models to near or below chance level (Section 07).
  • Every trained checkpoint is a single run — no seed averaging, so a different seed could move any number here by an unmeasured amount.
  • KMU-FED is 12 people in one stationary room, not live video from a moving car across changing light — a real step toward in-cabin conditions, not a simulation of driving itself.
  • The one live webcam session run so far used the original cnn_v1 on visible light, 42 minutes, one person — not yet repeated with a fine-tuned model or an IR camera.

None of this means the work isn't useful — it means every number above should be read with its sample size and caveats attached, not as a finished product. Full detail on every run, including the ones that didn't help, is in docs/experiment_log.md.
